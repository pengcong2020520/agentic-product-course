# 章节写法

一句话原则：**README 讲概念和道理，design.md 放参数和实现细节，代码只作佐证。**

## README 模板（每章一样，检查脚本强制）

```markdown
# sNN: 名称 — 一句话说明这一章让产品获得什么

导论 → s00 → … → `sNN` → … → app          ← 章节导航

> *"一句引语"* — 一两句解释这一章的核心道理。
>
> **对应问题框架**：③ …？ ⑥ …？            ← 用问题框架的原文

---

![本阶段在整体架构中的位置](images/architecture.svg)

## 要回答的问题
## 核心概念
## 分工：框架/平台做什么，我们做什么
## 跑起来看看
## 关键代码
## 小结
## 下一章
```

可以在"关键代码"之后加 `## 限制`、`## 多用户时会怎样`、`## 延伸` 等小节。

### 每节怎么写

- **要回答的问题**：第一句接上一章（"上一章做到 X，可是……"），然后用 3–5 个读者视角的问题列出缺口，最后一句"本章只加一个单元：**名称**"，并说明哪些原样沿用。
- **核心概念**：3–6 个 `###` 小节，每节先说"这是什么、为什么需要"，再说"怎么做"；只保留能帮助理解的关键数字（如"超过 10 秒没续上就算离开"），其余数值进 design.md。用读者能想象的场景解释（"旧主暂停 15 秒后醒来"）。
- **分工**：一张两列表"框架/平台做什么 | 我们做什么"，再补一两句人（运维/管理员）要做什么。
- **跑起来看看**：可运行的命令（离线实验在前、真实部署在后）；结尾一段"运行之后多了这些：……"（新目录、新表、新进程、数据存在哪）；长步骤、完整命令对照、环境变量清单链接到 design.md。
- **关键代码**：2–3 段，**逐行出自源码**（检查脚本会核对），每段前一句说明它证明了哪个概念。
- **小结**：4–6 条要点，每条一个概念。
- **下一章**：先用一两句写出新的缺口，再给链接；最后一章写明"这是主线最后一章"并指回完整项目。

### 不要写的东西（发现就改）

- 参数清单式的"核心概念"：一段里堆满参数名、秒数、环境变量；
- 项目改造史与新旧对比："原来/现在""本轮/本期""改造""第 0 步"；
- 只有链接、没有过渡的"下一章：[链接]"；
- 部署细节（Compose 项目名、systemd 单元名、内存上限、镜像源变量）出现在正文；
- 前文伏笔与后文实际设计矛盾（例如说"将来会有私有范围"，后面却决定只有系统范围）。

## design.md 模板（七节固定顺序）

```markdown
## 设计原理          为什么这样设计（2–4 段）
## 架构改进          在上一阶段之上加了什么、改了哪些边界
## 技术实现流程      关键流程，可含伪代码、时序；按主题用 ### 小节
## 核心代码          摘录与说明
## 验证              离线 / 真实依赖 / 部署三层，各自的命令
## 限制说明          已知边界
## 机制实验          npm run lesson -- … 列表与各自验证什么
## 关键数值与实现细节  全部参数、默认值、完整命令对照、部署步骤、限制的完整说明
```

## 导论、总览与术语

- 导论的问题框架总表"在哪一章"一栏必须和每章开头的标注一一对应（写脚本从各章抽取，对比后更新）。
- 一组"一句话说明"在根 README、导论章节表、阶段总览、路线图里用同一套措辞。
- 术语：`term / aka / stage / short / detail / related / source`；short 一句话，detail 讲清为什么；related 必须指向已有条目；由负责人亲自写。

## Web 课时与长文

- 与 README 同一条主线、同一套概念名称；长文可以更详细，但同样不写运维手册。
- 交互元素（测验、推演、源码摘录、术语、架构图）改正文时保持不动；源码摘录逐行一致。
- 跨章引用（"进入 sNN""见 sNN"）要随路线更新；边界说明（"本章不提供 X"）补上在哪一章兑现。
