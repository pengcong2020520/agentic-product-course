# 派活与审查

原则：**判断不外包**。范围、取舍、数值、验收标准由负责人写死；执行者交付后由负责人亲自审，下属审查只作补充。

## 任务说明模板（文件放仓库外，例如 `briefs/<任务名>.md`）

```markdown
# 任务：<一句话>（工作目录 = 仓库根，分支 <name>）
不要 git commit；不加依赖；不写个人信息；<其他固定约束>。
只改 <文件/目录>；不要改 <文件/目录>（其他任务正在改）。

## 背景与证据
<为什么做；返工时附实测数字、报错原文、定位到的代码行>

## 要做的事（数值已定，照做）
1. …（每条写清做什么、数值是多少、边界在哪）

## 验收清单（我会逐条核对）
1. <具体测试名 / grep 结果 / 命令与预期输出>
2. 离线 `npm test` 通过；跑不了的（端口、数据库、浏览器、Docker）写出命令与预期
3. 结果写 ~/…/briefs/<任务名>-result.md：改了哪些文件、每条验收对应的测试、拿不准的地方
```

### 每份说明都要写上的固定条款（来自踩过的坑）

- "依赖与参考快照一致；**不要手写任何库的替代实现**"（执行者曾为满足"不加依赖"手写协议与解析器）。
- "验收用的 grep 允许 <例外>；**不要为通过检查而改名**"。
- "关键数值按本说明，**不要自行提高门槛**"（执行者曾把部署要求定成 20 GB 磁盘）。
- "**不要把报告写进仓库**；结果写到指定路径"（`-o` 指定的文件会被最终摘要覆盖，结果文件另用一个路径）。
- "沙箱里跑不了的测试不要写进验证记录"（执行者曾把端口受限导致的失败写进仓库的验证文件）。
- 并行任务按目录拆开，互不改同一个文件。

## 调用方式（无交互）

```bash
# 写代码：显式给出工作目录、可写范围和结果文件路径
<执行者 CLI> --cwd <worktree> --write <允许写的目录> < <briefs>/<任务>.md > <briefs>/<任务>.log 2>&1
# 只读审查：换一个模型，提示里写明不要改文件，事后 git status 核对
<另一个执行者 CLI> --read-only --cwd <worktree> < <审查说明>
```

具体命令以所用工具的当前文档为准。

长时间任务放后台运行；会话中断后后台任务会停，先看工作区有无半成品再重派。

## 交付后的审查（负责人亲自做）

1. 读结果文件，**再读 diff 的关键部分**，不只看"测试通过"。
2. 逐条对照验收清单；抽查事实、数值与源码是否一致；补写的文字是否只概括了已有内容。
3. `git status`：删掉执行者写进仓库的报告、临时文件。
4. 补跑沙箱外的测试（见 quality-gates）；截图检查页面与图。
5. 需要时让另一个模型只读交叉审查，结论逐条复核后再决定是否采纳。
6. 不合格就写清具体问题打回；小问题自己改，在提交说明里写明分工（"代码由 <执行者> 编写，负责人审查、实测与修正"）。

## 打回的典型信号

- 为通过检查而改代码 / 改名 / 改断言，而不是修问题；
- 门槛、范围、依赖被擅自扩大；
- "全部通过"只是离线部分；
- 测试名与验收条目对不上；
- 文档里出现新的、无依据的说法。
