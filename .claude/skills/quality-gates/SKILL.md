# 质量关卡

离线测试通过不代表能用。很多问题只在真实系统用户、真实数据库、真实两台机器下才暴露。

## 三层验收（每个阶段都要过）

| 层 | 测什么 | 在哪里 | 典型发现 |
|---|---|---|---|
| 1 离线 | 逻辑、文档结构、源码摘录、实验 | 本机 / 执行者沙箱 / CI | 逻辑错误、文档漂移 |
| 2 真实依赖 | 真实 PostgreSQL / Redis、真实系统 uid 与权限、监听端口、浏览器 | 本机（端口、数据库、浏览器）；Linux 容器或服务器临时目录（uid、capability、外部服务） | 权限位、软链接、跨卷 rename、认证开启后的健康检查 |
| 3 真实部署 | 部署后用真实模型小额度跑通；故障注入（kill / pause / 断网）；多机实测 | 服务器 | 时序、网络、资源、跨地域时限 |

任务说明里写清三层各由谁、在哪里、用什么命令跑；沙箱跑不了的明确列出，由负责人补跑。

### 服务器临时测试环境的做法

- 代码 rsync 到临时目录（例如 `/root/<stage>test`），依赖装进独立数据卷；
- 起独立的数据库 / Redis 容器和独立网络，凭据临时随机生成、不落盘；
- 测试容器按生产同样的最小权限运行（例如 `--user 0:1000 --cap-drop ALL` 只加回需要的 capability、`no-new-privileges`）；
- 输出写到服务器上的日志文件、后台运行（避免 SSH 断开丢输出），跑完删除容器、网络、数据卷和目录；
- 不在本机启动会自动拉起其他项目的容器环境。

### 真实演练

- 用临时测试账号，跑完禁用；真实模型只做小额度验收，先确认费用；
- 故障类章节真的执行 kill / pause / 断网 / 恢复，记下时间（例如"9 秒接管"）、前后状态与用户可见的结果；
- 演练脚本本身也要核对：判读条件写错会得出错误结论。

## 三态判定

任何检查、验收、评判都有三种结果：**通过、不通过、没能判定**（脚本报错、超时、格式不对、数据缺失）。没能判定绝不默认为通过，要记为"待核对"并显示出来。

## 失败排查

- **偶发失败先找根因**：看具体报错（CI 用 `--log-failed`），在本机或同样环境复现；不要直接重跑合并。常见根因：并行冷启动超时、断言写得太宽（正则被随机临时目录名误命中）、依赖外部服务。
- **外部原因先保线上**：部署失败先确认线上仍在运行；镜像源故障就临时换源、完成后改回；磁盘不足先清缓存、未用镜像。
- **同类失败第二、三次出现时停下来**：核对前提是否成立。收尾已证明的部分，把问题写成限制或教学内容，向负责人说明后再决定方向。

## 完成标准

- 三层都有结果，且结果来自真实环境的完整运行（不是沙箱片段）；
- 每个"没能判定"都已处理或明确记录；
- 偶发失败有根因、有修复。
